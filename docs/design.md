# 화음 수리점 모바일 웹앱 개발 설계서

문서 버전 1.0 · 작성 및 출처 확인 2026년 10월 19일 · 산출물 Markdown

## 0 문서 목적과 구현 결정

이 문서는 음악이론을 처음 배우거나 다시 익히는 사람이 화음의 음을 직접 바꾸고 소리를 비교하는 모바일 웹 게임 **화음 수리점**의 개발 기준이다. 기획자, 프런트엔드 개발자, 음악 검수자, 사운드 디자이너, 접근성 및 품질 담당자가 같은 판정 규칙과 콘텐츠를 사용하도록 게임 규칙, 8개 주문, 화면, 오디오, 데이터, 저장, 테스트와 단계별 작업을 고정한다. 현재 산출물은 개발 설계이며 게임 구현·배포·교육효과 검증을 완료했다는 뜻이 아니다.

**첫 출시의 결정은 작고 분명하다.** C·F·G를 근음으로 하는 장3화음과 단3화음만 다룬다. 가상건반에서 한 음씩 골라 주문에 맞게 고치고, 수정 전후를 같은 조건으로 들으며, 왜 그 음을 고쳤는지 확인한다. 수리한 악기들은 마지막 짧은 합주에 참여한다. 경쟁 타이머, 생명, 연속 출석 압박, 실제 연주 인식, 계정, 결제는 넣지 않는다.

이 게임의 성공은 8개 주문을 빨리 통과하는 데 있지 않다. 안내가 사라져도 근음·3음·5음을 구별하고, 익숙하지 않은 배치에서 장·단의 차이를 설명하며, 수리 전후의 소리와 바뀐 음을 연결할 수 있는지 확인해야 한다. 이는 검증할 **설계 가설**이며 보장된 교육효과가 아니다.

### 0.1 결정 상태를 읽는 방법

- **필수**: MVP 출시에 필요한 계약. 변경하려면 콘텐츠·테스트를 함께 수정한다.
- **설계 가정**: 사용자·기기·예산이 확정되지 않아 잠정적으로 정한 값. 검증 전 사실로 표현하지 않는다.
- **후속**: 첫 MVP의 출시 차단 요건이 아니다. 데이터 확장 가능성만 남긴다.
- **검증 목표**: 아직 측정하지 않은 품질·학습 지표. 달성한 실적으로 표시하지 않는다.

### 0.2 핵심 범위 표

| 항목 | MVP 필수 | 이후 확장 |
|---|---|---|
| 화음 | C, Cm, F, Fm, G, Gm | 다른 근음, 전위, 감·증3화음, 7화음 |
| 배치 | 지정 음역의 기본 위치 3음 | 여러 옥타브, 넓은 배치, 중복음 |
| 입력 | 탭 선택 가상건반과 큰 음 버튼 | 선택적 MIDI 입력 |
| 학습 | 음의 역할, 반음, 장3도·단3도·완전5도 | 조성 속 기능, 진행, 성부 연결 |
| 콘텐츠 | 수리 주문 8개, 자유 실험, 8마디 합주 | 새로운 손님 묶음, 사용자 편곡 |
| 판정 | 음고·철자·배치 조건 분리 | 전위·성부·음역 조건 조합 |
| 저장 | 기기 내 진행과 설정, 내보내기·가져오기 | 동기화, 교사용 관리 |
| 배포 형태 | HTTPS 정적 웹앱, 반응형 | 검증 후 설치형 PWA·오프라인 확장 |
| 성과 확인 | 소규모 사용성 테스트, 별도 전이 평가안 | 대조 조건을 둔 교육효과 연구 |

### 0.3 구현 우선순위

1. 순수 음악 판정 함수와 8주문 정답을 먼저 검증한다.
2. 무음 상태에서도 사용할 수 있는 수리 화면과 복구 흐름을 만든다.
3. 수정 전후가 정말 다르게 들리는 오디오를 연결한다.
4. 최소 안내로 관계를 이해하는지 사용자 테스트를 한다.
5. 장식·손님 애니메이션·합주를 얹되 판정과 소리를 바꾸지 않는다.
6. 접근성·저장 실패·백그라운드 중단을 통과한 뒤 첫 공개 여부를 판단한다.

### 0.4 역할별 빠른 읽기

- 기획·교육 담당: 1~6장, 12장, 22~24장.
- UI·아트 담당: 7~9장, 17~18장.
- 오디오 담당: 10~11장, 17~18장.
- 개발 담당: 4장, 13~16장, 부록 A~B.
- 일정·출시 담당: 19~24장.

## 1 참고 자료에서 가져올 것과 독립적인 정체성

### 1.1 원문 확인 결과

사용자가 제공한 [음악 학습 앱과 음악 게임 5곳 비교](https://docs.google.com/document/d/1iXov6mc7A3DCGxOh8oCf5LAl468u_7R511OQxaH3lkk/edit)를 실제 읽고 반영했다. 원문은 2026년 10월 18일 확인 자료로 Rhythmic Village, Yousician, Simply Piano, DJMAX RESPECT V, beatmania IIDX를 비교한다. 제품의 공식 설명과 작성자의 장단점 추론을 구분하며, 게임 실력 향상이 실제 악기·이론 능력 향상을 보장하지 않는다고 명시한다. 이 설계는 원문을 제품 경험 비교 자료로 사용하며 다섯 제품의 교육효과를 입증된 순위로 인용하지 않는다.

| Simply Piano의 단계적 안내 | 첫 과제는 제한된 안내, 이후 도움을 점차 제거 | 매번 정답 건반을 밝혀 따라 누르게 하기 |

### 1.2 작품 구분

- 제품명: **화음 수리점**. 내부 프로젝트 ID: `chord-repair-shop`.
- 중심 이미지: 낮의 작은 악기 수리점, 투명한 오르골 속 세 개의 음 조각, 손님이 적어 둔 화음 주문서.
- 한 마디 조립실과는 별도 앱·폴더·저장 이름 공간을 쓴다. 같은 음악 기초 컴포넌트라도 콘텐츠와 진행은 합치지 않는다.
- 기존 리듬 마을 및 밤실 공방과도 독립이다. 기존 작품의 로고, Bits 계열 리듬 캐릭터, Melatonin을 연상시키는 꿈 장면·색 배치·잠자는 주인공·고유 연출은 사용하지 않는다.
- 상업 제품의 화면·음원·브랜드·캐릭터를 모사하지 않는다. 비교 자료의 서비스명을 앱의 마케팅 문구나 공동 개발 표시로 넣지 않는다.
- 색감과 도구 모양은 구현 전 독립적인 디자인 검토를 받는다. 최종 상표 사용 가능 여부는 아직 조사하지 않은 출시 결정 사항이다.

## 2 사용자와 학습 조건

### 2.1 명시적인 설계 가정

나이, 기존 악기 경험, 사용할 수업 환경은 확정되지 않았다. MVP는 한국어를 읽을 수 있고 화면을 탭할 수 있는 일반 음악 입문자를 기본으로 설계한다. 어린이 전용 또는 성인 전용으로 단정하지 않는다. 어린이를 대상으로 배포할 경우 별도의 사용자 조사·보호자 동의·개인정보 검토가 필요하다.

- 악기 소유·악보 읽기·절대음감은 시작 조건이 아니다.
- C·D·E 표기를 몰라도 `도 C`, `레 D`, `미 E`를 함께 볼 수 있다. 이 계이름은 **고정도 표기 보조**이며 이동도법·조성의 으뜸음을 뜻하지 않는다.
- 화면 세로 방향과 한 손 입력을 기본으로 하고 가로 방향·키보드·스크린리더도 허용한다.
- 1회 목표 이용 시간은 3~8분, 8주문 첫 체험은 쉬어 가기를 포함해 약 15~25분으로 가정한다. 출시 전 실제 관찰로 다시 정한다.
- 소리를 재생할 수 없는 환경에서도 시각적 구조 학습은 가능하다. 청각 구별 능력의 성취로 기록하지 않는다.
- 실제 피아노 손가락 번호·운지·자세·악보 독해를 가르친다고 주장하지 않는다.

### 2.2 사용자의 대표 질문

1. “장화음 주문인데 무엇을 바꿔야 하지?” → 주문의 근음·성질, 현재 음 관계, 비교 듣기를 제공한다.
2. “소리는 같은데 음이름은 왜 달라?” → 건반의 이명동음을 설명하고 주문 문맥에 맞는 철자를 보여 준다.
3. “다른 음까지 고쳤어. 처음부터 해야 해?” → 무제한 되돌리기와 원래 화음 복원, 최종 관계 판정으로 해결한다.
4. “음이 안 들려.” → 오디오 상태를 먼저 구별하고 진행을 보존한다.
5. “답은 맞혔는데 이해한 건가?” → 힌트 사용과 독립 해결을 구별하고 새로운 표현의 확인 문제를 제공한다.

## 3 핵심 플레이 루프

### 3.1 1주문 흐름

`주문 읽기 → 현재 소리 듣기 → 바꿀 음 선택 → 가상건반에서 교체 → 전후 비교 → 수리 확인 → 관계 확인 → 진열`

각 단계에서 사용자는 주문서를 다시 볼 수 있다. 소리를 꼭 여러 번 들어야 진행되는 식의 강제 조건은 없다. 음을 바꾸는 동안 정답 여부는 자동으로 공개하지 않고, 사용자가 `수리 확인`을 누를 때 판정한다. 정답이면 우선 “주문 조건에 맞아요”라는 짧은 확인만 표시하고, 관계 질문에 첫 답변하거나 건너뛴 뒤 자세한 변경 설명을 보여 준다. 그러므로 끝없는 녹색 점멸을 보고 답을 찾는 행동을 줄일 수 있다.

실험은 실패가 아니다. 수정 횟수, 듣기 횟수, 머문 시간에 감점을 주지 않는다. 잘못된 화음도 재생한다. 다만 “틀린 소리” 대신 “이 주문의 조건과 다른 부분”이라고 설명한다. C단3화음은 유효한 화음이며 C장3화음을 요구한 주문에서만 다른 답이다.

### 3.2 첫 핵심 장면

손님은 `C 장3화음`이라고 적힌 오르골을 맡긴다. 현재 음은 C4–E♭4–G4다. 사용자는 가운데 음 조각을 선택하고 E4로 바꾼다. 전후 비교 버튼을 누르면 같은 악기·크기·길이로 C4–E♭4–G4와 C4–E4–G4가 차례로 들린다. 확인 후에는 “근음 C에서 3음까지 거리가 3반음에서 4반음으로 바뀌었어요. 근음과 5음은 그대로예요.”라고 보여 준다.

이 장면에서 “밝아져서 정답”, “슬픈 소리가 나쁜 소리”라는 설명은 하지 않는다. 장·단의 정서는 개인과 문맥에 따라 달라질 수 있으며 정답 기준은 음 관계다. 감상 질문에는 “어떤 느낌으로 들렸나요?”를 선택적으로 쓸 수 있으나 정오 판정·저장·보상과 연결하지 않는다.

### 3.3 보상과 동기

- 주문을 완료하면 악기 한 점이 진열대에 놓인다. 같은 주문을 다시 해도 중복 재화를 지급하지 않는다.
- 결과는 `수리 완료`, `도움 없이 확인`, `연습 중`으로 구분한다. 빠름·우열·순위를 표시하지 않는다.
- 8주문을 완료하면 합주가 해금된다. 청각 과제는 접근성 때문에 필수 해금 조건으로 삼지 않는다.
- 도움을 받아도 수리 완료와 합주를 얻는다. 독립 이해 정보는 개인 학습 기록에만 분리한다.
- 사용자에게 주문별 음악 개념과 자신의 수정 이력을 짧게 보여 준다. 별 개수로 개념 이해를 단일 숫자로 환산하지 않는다.

## 4 정확한 음악이론 계약

이 장은 화면·오디오·정답·저장의 공통 기준이다. MIDI 숫자만으로 음이름을 추론하거나 화면 배열 위치만으로 화음의 역할을 정하지 않는다.

### 4.1 음 표현

| 개념 | 내부 표현 | 예 |
|---|---|---|
| 문자 이름 | `letter: C D E F G A B` | E |
| 변화표 | `accidental: -2 -1 0 1 2` | E♭은 -1 |
| 옥타브 | scientific pitch notation, 정수 | 가운데 도 C4 |
| 절대 음고 | MIDI 정수, C4=60 | E♭4=63, E4=64 |
| 음고류 | `mod(midi,12)` | E♭4·E♭5는 3 |
| 역할 | 목표 근음 기준 `root third fifth` | C 화음의 E/E♭은 third |
| 배치 | 실제 최저음과 오름차순 음고 | E4–G4–C5는 C/E |

정규형은 `{letter, accidental, octave}`다. `midi = 12 × (octave + 1) + naturalPc[letter] + accidental`로 계산한다. 계산 전에 0~127 범위인지 검증한다. 음고류는 음수에도 안전한 `((midi % 12) + 12) % 12`를 쓴다. 변화표는 음고 계산 마지막에 더하므로 B♯3=60, C♭4=59가 올바르게 된다. `octave`는 음이름의 문자 C를 경계로 정하는 표기이며 MIDI 음고를 나눠 덮어쓰지 않는다.

MVP의 실제 입력 음역은 C4~D5, MIDI 60~74다. 재생 엔진의 향후 지원 범위는 MIDI 48~84로 설계하지만 첫 콘텐츠의 검증 범위를 넓히지는 않는다. 이명동음·전위 테스트용 내부 fixture는 입력 화면에 노출하지 않아도 된다.

### 4.2 3화음과 역할

- 장3화음: 근음에서 장3도와 완전5도, 반음 간격 `[0,4,7]`.
- 단3화음: 근음에서 단3도와 완전5도, 반음 간격 `[0,3,7]`.
- 쌓은 3도 간격은 장3화음 `[4,3]`, 단3화음 `[3,4]`다. 두 번째 숫자는 근음으로부터의 거리가 아니다.
- `3음`은 화음 구성음의 역할이고 `3도`는 두 음 사이의 음정이다. 숫자 3을 “건반 세 칸”으로 설명하지 않는다.
- C–D–E를 셀 때 문자 이름을 포함하여 C에서 E까지 3도다. 검은건반을 포함한 반음 수로 장·단을 구별한다.
- 첫 주문에는 근음·3음·5음의 배치가 낮은 음부터 나란하지만, 역할을 항상 왼쪽·가운데·오른쪽이라고 정의하지 않는다.
- 이 세 음이 다른 순서로 울려도 화음의 정체성과 근음은 자동으로 바뀌지 않는다. 전위는 최저음의 역할이 무엇인지로 정한다.

장·단3화음의 구조 설명은 [Puget Sound 대학의 3화음 설명](https://musictheory.pugetsound.edu/mt21c/TriadsIntroduction.html)과 대조하여 검수한다. 아래 게임의 특정 주문·입력·판정 계약은 이를 적용한 독립 설계다.

### 4.3 이명동음과 철자

같은 평균율 음고라도 E♭와 D♯는 이름과 이론적 역할이 다를 수 있다. C단3화음의 3음은 E♭다. C–D♯–G를 정규 악보 표기상 C단3화음의 올바른 철자로 저장하지 않는다.

다만 MVP 가상건반의 검은건반은 하나의 물리 음고 입력이다. 사용자가 E♭/D♯ 건반을 눌렀다는 이유만으로 철자 오답을 만들면 안 된다. **음고 선택과 철자 선택은 별도 기능**이다.

1. 건반 이벤트는 MIDI 음고를 전달한다.
2. `spellForTask(midi, targetRoot, targetQuality)`가 목표 구성음과 같은 음고류이면 해당 구성음의 올바른 문자 철자를 부여한다.
3. 구성음이 아닌 음고에는 콘텐츠에 명시된 `displaySpellingMap`을 사용한다. 임의의 전역 샤프 치환을 하지 않는다.
4. MVP에서는 철자 선택 자체를 시험하지 않는다. 자동 표기된 음이름과 역할의 관계를 설명한다.
5. 후속 철자 과제는 D♯와 E♭를 구별해 고르는 UI를 제공하고, `spellingRequired=true`일 때만 별도 철자 판정을 한다.

### 4.4 조성과 화음의 구분

`C 장3화음`은 C–E–G라는 화음이며 `C장조`와 같은 말이 아니다. C·F·G 장3화음은 C장조의 주요 3화음으로 연결할 수 있지만, MVP는 조성 속 기능을 평가하지 않는다. Fm·Gm까지 포함한 주문 목록을 C장조의 다이어토닉 화음 목록으로 제시해서는 안 된다. 단조 음계·가락단음계·화성단음계는 이 버전의 학습목표 밖이다.

### 4.5 옥타브와 전위

기본 위치는 **근음이 최저음**인 상태다. C4–E4–G4와 C3–E4–G4는 모두 기본 위치지만 음역과 배치는 다르다. 제1전위는 3음이 최저음인 E4–G4–C5, 제2전위는 5음이 최저음인 G3–C4–E4다. C4–G4–E5는 순서가 넓어졌어도 기본 위치다.

기본 위치와 밀집 배치는 별개다. MVP는 기본 위치이면서 한 옥타브 안에 세 음을 둔 밀집 배치를 사용한다. 이 구분과 전위의 정의는 [Puget Sound 대학 음악이론 교재](https://musictheory.pugetsound.edu/mt21c/InvertedTriads.html)를 참고한다.

MVP는 지정된 조립 장치에 정확한 세 음고를 요구한다. `registerMode=exact`는 목표 MIDI **다중집합**과의 정확 일치이며 슬롯 배열 순서는 정답 조건이 아니다. 세 부품의 표시 위치를 바꾸어도 같은 세 음고라면 통과한다. 전위는 실제 최저 MIDI로 계산한다. 위치를 시험하는 후속 과제는 별도 `slotConstraint`를 설계해야 한다. 다른 옥타브의 C–E–G를 만들었다면 “화음 종류는 맞아요. 이 오르골의 음역 C4–E4–G4에 맞춰 주세요.”라고 설명해야 한다. 단순히 “화음이 틀렸어요”라고 말하지 않는다. `pitchClassCorrect`, `spellingCorrect`, `registerCorrect`, `inversionCorrect`를 분리하는 이유다.

### 4.6 정답 판정 순서

1. 입력 데이터가 유효한지 확인한다. 범위 밖·중복 ID·NaN·잘못된 문자 등은 콘텐츠/앱 오류이며 사용자 오답이 아니다.
2. 세 슬롯에 각각 한 음이 있는지 확인한다. 빈 슬롯은 `INCOMPLETE`.
3. 요청 근음과 성질로 목표 음을 계산하고 fixture의 목표 값과 일치하는지 확인한다.
4. 실제 음고류 **다중집합**을 목표와 비교한다. Set만 쓰면 C–E–E처럼 빠진 5음을 놓칠 수 있다.
5. 설정된 경우 철자·지정 음역·최저음 조건을 확인한다.
6. 조건이 모두 맞으면 최종 정답이다. 사용한 변경 횟수·되돌리기·수리 확인 횟수는 판정에 관여하지 않는다.
7. 응답은 오류 코드와 학습용 원인으로 반환한다. 한국어 문구는 UI 계층에서 만든다.

판정 코드: `INVALID_DATA`, `INCOMPLETE`, `ROOT_MEMBER_MISSING`, `THIRD_MISMATCH`, `FIFTH_MISMATCH`, `MEMBERS_MISMATCH`, `REGISTER_MISMATCH`, `INVERSION_MISMATCH`, `SPELLING_MISMATCH`, `CORRECT`. 여러 문제가 있으면 콘텐츠 안전 오류가 우선이고, 그다음 빠진 구성음·배치 조건을 설명한다. 여러 오답을 한 문장에 나열하지 말고 도움 수준에 맞춰 하나씩 보여 준다.

## 5 MVP 교육과정과 8개 주문

### 5.1 공통 데이터 읽기

모든 음 표기는 낮은 음부터 적는다. `♭`은 flat, `♯`은 sharp다. MIDI 값과 음이름을 함께 검수한다. 첫 6주문은 3음 교체를 익히고 7~8주문에서 5음·근음을 점검하여 “무조건 가운데만 누르면 된다”는 습관을 깨뜨린다. 최소 변경 횟수는 콘텐츠 분석용이며 보너스·통과 조건이 아니다.

| CR01 | C 장3화음 | C4 E♭4 G4 | C4 E4 G4 | 3음 | 3음 슬롯만 열림, 반음 안내 |

### 5.2 CR01 처음 맡긴 오르골

- 손님 주문: “C를 근음으로 하는 장3화음으로 맞춰 주세요.” 목표 이름을 숨겨 청음만으로 맞히게 하지 않는다.
- 시작 MIDI `[60,63,67]`, 목표 `[60,64,67]`. 수정 가능 슬롯 `third`, 나머지는 잠금 아이콘과 “이번 연습에서는 고정” 설명.
- 첫 시도 전: 현재 화음을 동시에 0.9초 재생하거나 한 음씩 재생할 수 있다.
- 학습 안내: C→D♭→D→E♭→E의 **반음 이동 4회**를 도구에서 확인한다. 출발 음까지 세어 “다섯 칸”이라고 혼동하지 않도록 선분 4개로 표시한다.
- 입력: 3음 선택 → 건반 E4 탭 → 현재 화음이 바뀜 → 수리 확인. E4를 계속 점멸시키지 않는다. 사용자가 3단계 도움을 요청했을 때만 정답을 한 번 보여 준다.
- 오답 예: D4 `[60,62,67]` → “장3화음의 3음은 근음보다 4반음 위에 있어요. C에서 하나씩 세어 볼까요?”
- 정답 후 질문: “바뀌지 않은 두 음은?” 선택지 `C와 G / C와 E / E와 G`, 정답 `C와 G`. 도움을 사용해도 진행한다.
- 완료 화면: 원래·수리 후 음이름과 소리를 함께 비교. 전후 음색 변경 금지.

### 5.3 CR02 반대로 고치기

- 주문 C 단3화음, 시작 `[60,64,67]`, 목표 `[60,63,67]`.
- 3음만 편집 가능하지만 올릴지 내릴지는 사용자가 결정한다.
- CR01을 기계적으로 반복하여 E를 올렸을 때는 “이번 주문은 단3화음이에요. 근음과 3음의 거리를 확인해 보세요.”라고 한다.
- 정답 후 관계 질문: “C에서 E♭까지는 몇 반음?” `3 / 4 / 7`, 정답 `3`.
- 성공 표현: “근음과 5음은 두고 3음을 반음 내렸어요.” 감정어를 정답 설명으로 쓰지 않는다.

### 5.4 CR03 다른 근음에서도 같은 관계

- 주문 F 장3화음, 시작 `[65,68,72]`, 목표 `[65,69,72]`.
- 세 슬롯 편집 가능. 원래 정답인 F·C를 바꿔도 즉시 막지 않는다. 최종 상태를 판정한다.
- 도움 1: “근음이 F로 바뀌었어요. 장3화음의 간격 규칙은 같아요.” 도움 2에서 F→A 4반음만 시각화한다.
- 정답 후: “장3화음을 만들 때 유지되는 관계는?” `근음에서 3음 4반음 / 항상 E를 넣기 / 검은건반을 쓰지 않기`, 정답 첫 항목.
- C5가 화면 밖에 있더라도 슬롯 카드에는 C5를 계속 표시하고 `C5 위치 보기`로 건반을 스크롤할 수 있다. 자동 스크롤은 사용자 입력을 빼앗지 않는다.

### 5.5 CR04 검은건반과 음이름

- 주문 G 단3화음, 시작 `[67,71,74]`, 목표 `[67,70,74]`.
- B♭4를 택하면 건반 보조 표기는 `B♭ / A♯`, 슬롯의 문맥 표기는 `B♭4`다.
- 도움 1은 “G에서 3음까지의 거리를 확인해 보세요.” 도움 2에서 G→B♭ 3반음을 표시한다.
- 결과 설명: “G의 단3도 위 음은 B♭이에요. 이 건반은 A♯로도 부르지만 여기서는 3음의 문자 이름 B를 씁니다.”
- 확인 질문: “이번 화음의 3음은?” `G / B♭ / D`, 정답 `B♭`. 철자 두 개를 선택하게 하는 시험은 아직 하지 않는다.

### 5.6 CR05 도움 없는 장3화음 확인

- 주문 G 장3화음, 시작 `[67,70,74]`, 목표 `[67,71,74]`.
- 들어가기 전 규칙 툴팁 자동 노출 없음. 역할 이름은 숨길 수 있지만 기본 표시 설정은 사용자의 선택을 따른다.
- `힌트`를 누르면 도움 모드로 전환하고 `independent=false`로 기록한다. 수리 보상은 같다.
- 정답 후: “G 단3화음과 비교해 무엇이 달라졌나요?” `3음이 반음 높아짐 / 근음이 바뀜 / 5음이 반음 낮아짐`, 정답 첫 항목.
- 잘못 고른 음을 되돌렸다가 다시 맞혀도 수리 완료한다. 첫 제출 정오와 최종 성공은 따로 기록한다.

### 5.7 CR06 도움 없는 단3화음 확인

- 주문 F 단3화음, 시작 `[65,69,72]`, 목표 `[65,68,72]`.
- 정답 후 확인: “F→A♭, F→C의 반음 수는?” `3과 7 / 4와 7 / 3과 6`, 정답 `3과 7`.
- 초보에게 숫자 질문이 부담이면 `간격 그림 보기`를 열 수 있다. 열었다면 해당 개념 확인은 도움 사용으로 구분한다.
- “단화음은 검은건반 하나” 같은 규칙을 설명하지 않는다. 이후 A단3화음은 모두 흰건반이라는 전이 예시가 이를 점검한다.

### 5.8 CR07 가운데 음만 고치지 않기

- 주문 C 장3화음, 시작 `[60,64,66]`, 목표 `[60,64,67]`.
- 목표의 근음과 3음은 이미 맞고 마지막 음은 F♯4다. F♯은 근음 C의 완전5도가 아니다.
- 최초 화면에서 특정 슬롯을 강조하거나 “5음을 고치세요”라고 공개하지 않는다. 사용자가 어떤 관계를 점검하는지 관찰한다.
- 오답으로 E를 E♭로 바꾸면 “현재는 주문의 3음과 5음을 함께 확인해야 해요.”라고 도움 수준에 맞춰 설명한다. 자동 복원하지 않는다.
- 정답 후: “장·단3화음에서 근음과 5음의 간격은?” `7반음 / 3반음 / 4반음`, 정답 `7반음`.
- 새 개념을 무예고로 시험하지 않는다. CR03 이전부터 5음 7반음 관계를 보여 주고, CR07 직전 선택형 짧은 복습을 제공하되 특정 정답 슬롯은 말하지 않는다.

### 5.9 CR08 주문의 근음 확인

- 주문 F 단3화음, 시작 `[64,68,72]` 즉 E4–A♭4–C5, 목표 `[65,68,72]`.
- 오르골에 들어 있는 음을 “E 장조” 등으로 임의 명명하지 않는다. 시작 화음은 주문 조건과 다른 음 모음으로 소개한다.
- 이름이 F로 시작하는 주문의 근음 역할을 확인하고 E4를 F4로 바꾸는 과제다. 전체 음고류와 음역 조건을 만족하면 어떤 탐색 경로도 정답이다.
- 정답 후 확인: “F단3화음의 근음과 3음은?” `F와 A♭ / A♭와 C / E와 A♭`, 정답 `F와 A♭`.
- 마지막 안내: “이제 음의 위치가 달라져도 같은 관계인지 살펴볼 수 있어요.” 전위 강좌를 이미 배웠다고 기록하지 않는다.
- CR08 수리 후 합주를 해금한다. 8개 확인 질문은 재시도 가능하며 한 질문 오답으로 악기를 회수하지 않는다.

### 5.10 콘텐츠의 반복과 난이도

첫 순서는 CR01→CR08로 고정한다. 완료 후 자유 재방문은 모든 주문을 허용한다. 첫 MVP에는 무작위로 오답 음을 생성하지 않는다. 의도하지 않은 감화음·중복음·음역 초과가 학습목표를 흐릴 수 있기 때문이다. 정답 목록을 섞는 간단한 선택지 순서는 seeded shuffle로 기록 가능하게 한다. 정답 버튼 위치가 항상 같아지지 않도록 하고 스크린리더 읽기 순서와 시각 순서를 일치시킨다.

## 6 튜토리얼과 도움 체계

### 6.1 첫 실행 약 90초 안내

| 단계 | 화면 문구 | 사용자 행동 | 완료 조건 |
|---|---|---|---|
| T0 | “소리를 들으며 고쳐 볼까요? 처음에는 작은 소리로 시작하세요.” | 소리 켜기 또는 소리 없이 시작 | 명시적 선택 |
| T1 | “주문은 C 장3화음이에요.” | 주문서 확인 | 확인 버튼 |
| T2 | “오르골에는 세 음이 들어 있어요.” | 원래 듣기 또는 음이름 보기 | 보기만 해도 진행 가능 |
| T3 | “C는 근음, E♭는 3음, G는 5음 역할이에요.” | 각 음 카드 탐색 | 다음 버튼 |
| T4 | “오늘은 3음을 바꾸어 볼게요.” | 3음 카드 탭 | 편집 패널 열림 |
| T5 | “원하는 음을 골라 소리를 비교해 보세요.” | E 또는 다른 음 탐색 | 음 1회 선택 |
| T6 | “준비되면 수리 확인을 누르세요.” | 제출 | 판정 반환 |
| T7 | “무엇이 바뀌었는지 비교해 볼까요?” | 전후 비교 또는 설명 읽기 | 사용자가 완료 |

T4까지는 조작과 역할 안내, T5부터는 사용자의 탐색이다. 정답을 자동 입력하는 경우에는 `시범 보기`라고 표시하고 독립 해결 기록을 남기지 않는다. 언제나 `건너뛰기`, `다시 보기`가 있다. 말풍선이 버튼을 덮으면 안 된다. 튜토리얼은 포커스를 현재 단계로 이동하되 뒤로 가기와 종료를 막지 않는다.

### 6.2 3단계 도움

1. **관계 다시 보기**: 주문의 조건만 설명. 예 “장3화음은 근음에서 3음까지 4반음이에요.”
2. **거리 확인 도구**: 선택한 두 음 사이의 반음 수와 목표 거리를 함께 표시. 정답 음 자체를 자동 선택하지 않는다.
3. **수리 시범**: 바꿀 역할과 목표 음을 보여 주고 한 번 시연. 현재 상태를 백업한 뒤 사용자가 `내 상태로 돌아가기` 또는 `시범 상태로 연습`을 선택한다.

도움은 시간 경과만으로 자동 팝업하지 않는다. 두 번 확인 실패 뒤 버튼 옆에 짧게 “관계 도구를 열 수 있어요”라고 제안할 수 있지만 계속 누르라고 재촉하지 않는다. 도움 수준은 주문 시도 전체의 최대값과 개념 질문의 최대값을 따로 저장한다.

### 6.3 피드백 문구 규칙

- “틀렸어요”만 표시하지 않는다. 주문 조건, 현재 관계, 다음 탐색 행동 중 최소 두 개를 담는다.
- 잘못된 모든 음을 빨간색으로 표시하여 정답을 역추적하게 하지 않는다. 기본 피드백은 조건 수준이고 자세한 슬롯 정보는 도움 단계로 제공한다.
- 오답 경고음·충격·화면 흔들기·손님의 실망 표정은 사용하지 않는다.
- 정답 때도 즉시 큰 음량의 팡파르를 겹치지 않는다. 화음을 들은 다음 작은 완료 소리와 진열 애니메이션을 재생한다.
- 관계 질문을 틀리면 “수리는 맞았어요. 이유는 한 번 더 살펴볼까요?”라고 결과를 구별한다.

## 7 조작과 모바일 터치 계약

### 7.1 기본 입력

기본 동작은 `음 슬롯 선택 → 음 선택 → 비교/확인`이다. 드래그, 세 손가락 동시 입력, 긴 누르기, 박자에 맞춘 탭은 필수 동작이 아니다. 큰 음 버튼과 가상건반은 같은 `SELECT_PITCH(midi)` 이벤트를 발생시킨다.

- 세 음 슬롯은 클릭 가능한 실제 button 요소다. 선택 상태는 테두리·문자 `선택됨`·ARIA 상태로 표현한다.
- 편집 패널을 열면 현재 음에 포커스. 목표 정답에는 포커스를 옮기지 않는다.
- 일반 수리 모드에서 음 선택은 `click` 또는 취소되지 않은 탭으로 확정한다. 터치 스크롤 시작 후 발생한 pointercancel은 음 변경으로 처리하지 않는다.
- 건반 `pointerdown`은 짧은 미리듣기만 시작할 수 있고 실제 교체는 click에서 한 번만 한다. 미리듣기는 0.35초 뒤 자동 종료하므로 pointerup 유실이 지속음을 만들지 않는다.
- 더블탭·반복 click은 같은 값이면 상태 revision을 늘리지 않는다. `event.repeat`로 중복 키 입력을 통제한다.
- 모든 편집은 `되돌리기`로 취소 가능. 최대 50개 변경 스냅샷을 메모리에 보관하고 주문 전환 때 지운다.
- `원래대로`는 해당 주문 시작음으로 복원한다. 이미 한 수정이 있을 때 확인 UI를 보여 주며 설정·완료 기록은 건드리지 않는다.

### 7.2 작은 화면의 가상건반

일반 피아노의 검은건반 구조를 유지하면서 모바일 입력을 과하게 축소하지 않는다.

- 키보드 음역 C4~D5를 수평 스크롤 가능한 영역에 표시한다. 기본 흰건반 폭 56 CSS px, 검은건반 폭 36px, 흰건반 높이 144px, 검은건반 높이 88px.
- 키보드 전체를 320px 화면에 강제 축소하지 않는다. 양쪽에 다음 음역 표시와 `낮은 쪽/높은 쪽` 버튼을 제공한다. 스크롤바·스크롤 힌트를 숨기지 않는다.
- 기본 선택지는 사용자가 편한 `가상건반` 또는 `큰 음 버튼`이다. 큰 음 버튼은 4열, 최소 48×48px, 간격 8px로 C4~D5 모든 반음을 제공한다.
- 검은건반 36px는 제품의 일반 44px 목표보다 작다는 점을 명시한다. 겹치는 히트 영역을 억지로 늘리지 않고 큰 음 버튼이라는 동등 기능을 항상 제공한다. 실제 손가락 테스트에서 오탭이 많으면 기본 입력을 큰 음 버튼으로 바꾼다.
- 키보드와 큰 음 버튼은 `touch-action: auto`를 사용해 브라우저의 확대·수평/세로 스크롤을 허용한다. 가로 스크롤 컨테이너의 범위만 CSS overflow로 지정한다. 스크롤로 취소된 pointer는 음 교체에서 제외하며 preventDefault로 pinch 확대를 막지 않는다.
- 오디오 재생 중 정답 건반은 켜지지 않는다. 현재 울리는 음 표시 옵션은 이미 사용자가 선택한 음만 보여 주고 평가 모드에서는 끌 수 있다.

### 7.3 키보드 및 보조기기

- Tab으로 주요 그룹 이동, 방향키로 음 선택, Enter/Space로 실행, Escape로 편집 패널 닫기.
- 건반 그룹은 roving tabindex로 15번의 Tab을 요구하지 않는다. 현재 음의 이름·옥타브·선택 상태를 읽는다.
- 기본 문자 키를 임의로 전역 단축키에 할당하지 않는다. 입력 필드·스크린리더 탐색과 충돌하는 단축키는 선택 설정으로 둔다.
- 소리 듣기와 음 교체를 스크린리더에서 별도 명령으로 사용할 수 있게 한다. 음 변경 결과는 polite live region에서 한 번만 읽는다.
- 브라우저 뒤로 가기나 패널 닫기 후 포커스는 원래 음 슬롯으로 돌아간다. 화면 전환 시 첫 제목으로 이동한다.

### 8.2 작업대 세로 배치

390×844 CSS px를 대표 설계 크기로 삼되 고정 높이에 맞춰 자르지 않는다. safe-area와 브라우저 주소창을 포함하여 실제 가용 높이를 사용한다.

1. 상단 48px 내외: 뒤로, `주문 3 / 8`, 음소거. 뒤로 버튼은 최소 44×44px.
2. 주문서 80~112px: `F 장3화음`, “근음 F · 3음 4반음 · 5음 7반음”은 도움 설정에 따라 접힘.
3. 오르골 96px 내외: 장식·음 조각. 장식만 클릭해야 기능이 되는 구조를 피한다.
4. 3음 카드 72px 이상: 현재 음이름/역할/선택 상태. 한 줄 3열이 읽기 어려우면 세로 목록으로 재배치.
5. 듣기 행: `원래`, `현재`, `전후 비교`, `정지`. 버튼은 아이콘과 글자 병행.
6. 입력 패널: 가상건반 또는 큰 음 버튼. 세로 공간이 부족하면 접을 수 있고 본문이 스크롤된다.
7. 하단 행동: `되돌리기`, `도움`, `수리 확인`. 하단 고정 영역이 마지막 음이나 확대된 텍스트를 가리지 않도록 같은 높이의 여백을 확보한다.

320px 너비·200% 확대에서는 장식 비중을 줄이고 한 열 작업 흐름으로 바꾼다. 400% 확대에서 주요 기능이 재배치되며 페이지 전체의 가로 스크롤을 만들지 않는다. 가상건반 내부의 본질적 2차원/수평 탐색은 별도이고, 동일 기능의 음 버튼을 제공한다. 화면 회전을 요구하지 않는다.

### 8.3 상태를 보이는 문구

- 오디오 잠김: “소리를 켜려면 눌러 주세요.”
- 백그라운드 복귀: “작업은 그대로예요. 다시 듣기를 누르면 재생돼요.”
- 무음 학습: “소리 없이 음 관계를 살펴보는 중이에요.”
- 저장 실패: “이번 기기에 진행을 저장하지 못했어요. 현재 작업은 계속할 수 있어요.” + 내보내기.
- 데이터 불일치: “이 주문을 불러오지 못했어요. 다른 주문으로 돌아가거나 다시 시도해 주세요.”
- 업그레이드 대기: “새 버전이 있어요. 지금 작업을 저장한 뒤 시작 화면에서 바꿀 수 있어요.”

### 8.4 접근성 수용 기준

WCAG 2.2 AA를 목표 기준으로 삼되 실제 적합성을 검증 전 주장하지 않는다. WCAG는 키보드 접근, 대비, 색상 외 정보, 확대·리플로, 포커스, 타깃 크기 등 개별 기준을 제공한다. [W3C WCAG 2.2](https://www.w3.org/TR/WCAG22/)

- 일반 본문 대비 4.5:1 이상, 큰 글자 3:1 이상, 필수 UI 경계·상태 대비 3:1 이상을 검수한다.
- 일반 주요 버튼은 44px 이상을 제품 목표로 삼는다. WCAG 2.2 AA의 타깃 최소 크기 24 CSS px 기준과 제품 목표를 혼동하지 않는다.
- 색 외에 역할 이름·도형·윤곽·음이름을 제공한다. 장·단을 녹색/빨강으로 구분하지 않는다.
- 자동 음성·자동 재생을 하지 않고 음소거·정지·음량을 계속 접근 가능하게 한다.
- `prefers-reduced-motion`을 초기값으로 반영한다. 별도 설정에서 정적인 완료 장면을 선택할 수 있다.
- 음높이를 듣는 기능에는 시각 설명 대체를 제공한다. 대체 경로의 성취는 청음 능력과 구분한다.
- 화면낭독기만으로 CR01~CR08 수리, 결과 확인, 설정, 저장 내보내기를 수행할 수 있어야 한다.
- 초당 번쩍임·펄스·동시 확대를 사용하지 않는다. 진열 애니메이션은 300ms 이하, 건너뛰기 가능.

## 9 아트와 사운드 자산 명세

### 9.1 시각 방향

낮의 악기 작업대, 종이 주문서, 서로 다른 형태의 세 음 조각을 기본 모티프로 한다. 따뜻한 배경과 명료한 잉크색을 쓰되 채도만으로 정답을 구별하지 않는다. 인간·동물 손님은 4명 기본형의 표정·소품을 조합해 8주문을 구분한다. 연령 가정이 미정이므로 지나치게 유아용인 대사나 아동만을 암시하는 이름을 피한다.

기능 UI는 DOM, 장식은 SVG 또는 작은 WebP로 구현한다. 글자는 이미지 안에 박지 않는다. 음이름, 변화표, 주문번호는 실제 텍스트로 렌더링한다. 음악 기호 글꼴은 ♭·♯가 모든 목표 기기에서 구분되는지 확인하고 접근성 이름에는 “플랫”, “샵”을 쓴다.

### 9.2 MVP 자산 목록

### 9.3 교육용 음색 기준

화음을 배우는 동안 수정 전후는 동일한 `reference` 음색이다. 비교 도중 리버브·옥타브·음량·연주 순서를 바꾸지 않는다. 손님의 악기 외형과 합주 음색은 보상 연출에 사용할 수 있지만 정답 힌트로 작동하지 않게 한다. 순수 사인파만이 유일한 기준은 아니며, 기본음이 분명한 부드러운 짧은 음색을 선택해 저가 스마트폰에서도 3음을 구별할 수 있는지 테스트한다.

## 10 오디오 시스템

### 10.1 기술 기준

MVP는 외부 녹음 샘플이나 저작권 곡 없이 Web Audio API로 작은 음색을 합성한다. `AudioContext`는 하나를 재사용하고 첫 사용자 동작에서 생성/재개한다. 자동 재생이 허용된다고 가정하지 않는다. Web Audio의 예약 재생과 AudioParam 자동화를 사용하며 UI 타이머를 음의 기준 시계로 삼지 않는다. 이는 [MDN Web Audio 권장사항](https://developer.mozilla.org/en-US/docs/Web/API/Web_Audio_API/Best_practices) 및 [AudioContext](https://developer.mozilla.org/en-US/docs/Web/API/AudioContext)의 동작을 바탕으로 한 설계다.

2026년 10월 확인 시 Web Audio 1.1 최신 문서는 Working Draft다. 새로운 초안 기능을 필수 기능으로 채택하지 않는다. 널리 구현된 `AudioContext`, `GainNode`, `OscillatorNode`, `AudioBufferSourceNode` 중심으로 구현하고 추가 API는 기능 탐지한다. 안정된 기준 문서는 [Web Audio 2021 Recommendation](https://www.w3.org/TR/2021/REC-webaudio-20210617/), 진행 중 사양은 [Web Audio 1.1](https://www.w3.org/TR/webaudio/)이다.

### 10.2 음 생성과 믹싱

- 조율 기준 A4=440Hz, 12평균율. `frequency = 440 × 2^((midi - 69) / 12)`.
- 기준 음색: 기본음 1.0, 2배음 0.18, 3배음 0.08의 정규화된 합성. 실제 최대 주파수가 Nyquist 미만인 배음만 사용한다.
- 기준 envelope: attack 8ms, decay 70ms, sustain 0.55, release 120ms. 기본 note gate 0.9초. 수치는 초기 제작값이며 청감·클릭·음량 테스트 후 버전 관리한다.
- 3화음의 각 음은 동일한 velocity. 처음에는 master gain 0.35로 시작하고 사용자가 바꿀 수 있게 한다. 이 값은 음압 안전을 보장하지 않으므로 실제 기기 음량 조절 안내를 표시한다.
- 각 voice 최대 진폭을 정규화하고 동시 voice 수에 맞춘 headroom을 둔다. 리미터에만 의존하여 clipping을 숨기지 않는다. 전체 출력 샘플 peak 목표는 -1dBFS 이하.
- 좌우 panning은 보상용 합주에만 약하게 사용하며 mono에서 정보가 사라지지 않아야 한다.
- 비교 듣기의 배경음악은 항상 멈춘다. 버튼 효과음이 화음의 첫 음을 덮지 않게 한다.
- 기본 동시 voice 상한은 24. 초과 시 오래된 낮은 우선순위 preview를 8ms fade-out하고 정답 비교의 3음은 함께 유지한다.

### 10.3 전후 비교 타임라인

사용자가 누른 순간의 현재 화음을 immutable snapshot으로 고정한다. 재생 중 수정하면 기존 비교를 취소하고 “음이 바뀌었어요. 다시 비교해 주세요.”라고 표시한다.

| 시점 | 동작 |
|---:|---|
| t0 | 화면에 원래/현재 버전과 음이름 표시 |
| t0 + 0.05s | 원래 화음 3음을 같은 시작 시간에 재생 |
| t0 + 0.95s | 원래 gate 종료, release 시작 |
| t0 + 1.35s | 현재 화음 3음을 동시에 재생 |
| t0 + 2.25s | 현재 gate 종료, release 시작 |
| t0 + 2.40s | 비교 종료 상태, 다시 듣기 활성 |

중간 0.4초는 원래 gate 종료 기준이며 0.12초 release를 포함해 잔향이 사라지도록 둔 값이다. 첫 비교에는 동시 화음만 재생한다. `한 음씩`은 별도 모드로 0.45초 간격의 세 음과 마지막 동시 화음을 재생하며 정해진 낮은 음순을 사용한다. 원래/현재를 동시에 겹쳐 재생하지 않는다.

### 10.4 시계와 스케줄러

수리 미리듣기는 현재 AudioContext 시간에 5~20ms 안전 여유를 더해 시작한다. 합주는 `AudioContext.currentTime` 기반의 25ms 조회/100ms look-ahead를 초기값으로 사용하는 짧은 스케줄러다. setTimeout은 큐 보충에만 사용하고 음 시작 시간은 `source.start(audioTime)`에 전달한다. 자바스크립트 시계와 오디오 시계를 분리하는 이유는 [Google web.dev의 오디오 스케줄링 설명](https://web.dev/articles/audio-scheduling)에서 확인할 수 있다. 숫자 25ms/100ms는 표준 보장이 아니라 이 앱의 조정 가능한 초기값이다.

```ts
type ScheduledVoice = { source: AudioScheduledSourceNode; gain: GainNode; generation: number };
// 개념 예시. 실제 구현은 취소, context 상태, 예외 처리까지 포함한다.
function scheduleTick() {
  if (audioState !== "running" || document.hidden) return;
  const horizon = ctx.currentTime + 0.100;
  while (nextEvent && nextEvent.at < horizon) {
    if (nextEvent.at >= ctx.currentTime + 0.005) schedule(nextEvent, generation);
    else handleLateEvent(nextEvent); // 뒤늦은 음을 한꺼번에 몰아 재생하지 않는다.
    nextEvent = takeNext();
  }
  timer = window.setTimeout(scheduleTick, 25);
}
```

지연 이벤트가 생기면 현재 합주를 멈추고 재시작 버튼을 보여 준다. 정답/오답으로 처리하지 않는다. 캔버스 애니메이션이 음을 재생시키지 않으며 UI 진행선은 오디오 시간에서 파생한다. requestAnimationFrame이 늦어져도 음 시작 예약은 바뀌지 않는다.

### 10.5 지연 처리

- MVP는 타이밍 점수를 매기지 않으므로 Bluetooth·OS 출력 지연 때문에 사용자를 감점하지 않는다.
- 목표 지표를 분리한다. 입력 처리→오디오 예약은 앱 지표, 손가락→실제 소리는 하드웨어 실측 지표다.
- `baseLatency`·`outputLatency`는 전체 손가락-스피커 지연의 확정 측정값이 아니다. 제공되지 않거나 부정확할 수 있으므로 기능 탐지 후 진단용으로만 쓴다.
- 시각 음표와 출력 시각을 맞출 때 가능한 기기에서는 `getOutputTimestamp()`의 오디오/성능 시계 매핑을 사용한다. 없으면 currentTime 기반 근사와 정적 표시를 쓴다. [MDN getOutputTimestamp](https://developer.mozilla.org/en-US/docs/Web/API/AudioContext/getOutputTimestamp)
- 장치가 바뀌면 이전 측정치를 폐기한다. 실제 타이밍 평가가 없는 MVP에 탭 보정 테스트를 강요하지 않는다.

### 10.6 중단과 복귀

`visibilitychange`, `pagehide`, 오디오 상태 변화를 감시한다. 브라우저는 백그라운드에서 타이머·애니메이션을 제한할 수 있으므로 계속 재생된다고 가정하지 않는다. [MDN Page Visibility API](https://developer.mozilla.org/en-US/docs/Web/API/Page_Visibility_API)

화면 숨김 시: generation 증가 → 스케줄러 취소 → 활성 voice 10ms fade → 예약 source stop → 필요한 상태 저장 → context suspend를 시도한다. suspend 실패와 관계없이 UI는 중단 상태다. 복귀 시: 자동으로 음을 내지 않고 `다시 듣기` 입력에서 resume → 현재 악기·화음으로 새 재생을 시작한다. 오래된 큐를 이어 붙이지 않는다.

전화·음성 도우미·잠금·이어폰 해제 등은 운영체제마다 다르므로 실제 기기에서 검사한다. `running` 외 상태는 새 음 스케줄링을 막는다. 명시적 `interrupted` 상태가 제공되는 브라우저에서는 중단으로 취급하되 문자열 지원에 의존하지 않고 공통 fallback을 둔다. 오디오가 닫혔으면 사용자의 다시 듣기 입력에서 새 context와 노드를 만들고 상태를 복원한다. 연속 실패 시 시각 학습을 계속할 수 있다.

### 10.7 오디오 실패 복구

| 실패 | 사용자 메시지 | 앱 처리 |
|---|---|---|
| autoplay 제한 | 소리를 켜려면 눌러 주세요 | 클릭에서 resume 재시도 |
| AudioContext 미지원 | 이 브라우저에서는 소리 재생을 사용할 수 없어요 | 시각 모드·지원 브라우저 안내 |
| 합성/샘플 생성 실패 | 소리를 준비하지 못했어요 | 기본 사인 음색으로 1회 fallback |
| 출력 장치 변경 | 다시 듣기를 눌러 주세요 | 큐 폐기, 새 시간 기준 |
| 백그라운드 중단 | 작업은 그대로예요 | 재생만 멈춤, 답 보존 |
| 반복 재생 버튼 폭주 | 추가 오류 문구 없음 | 이전 generation 취소, 마지막 요청만 재생 |

## 11 수리한 악기들의 합주

### 11.1 음악적 의미

모든 수리 화음을 한꺼번에 울리면 C/Cm, F/Fm, G/Gm의 3음이 충돌할 수 있다. 그러므로 “여덟 개를 동시에 켜면 합주”로 구현하지 않는다. 완료한 물건들이 각 마디에 맡은 화음을 들려주는 **교대 합주**를 기본으로 하고, 각 화음의 근음·3음·5음을 서로 다른 음색이 나누어 연주하는 짧은 반주로 만든다.

### 11.2 확정 합주 악보 데이터

템포 80 BPM, 4/4, 8마디. 1박은 0.75초, 1마디 3초, 전체 본문 24초. 마지막 잔향 0.4초. 조성 분석·성부 연결을 가르치기 위한 예시는 아니며, 장·단의 관계를 차례로 되짚는 원작 합성 모음이다.

| 마디 | 주문 악기 | 화음 | 낮은음/중간음/높은음 MIDI | 세 파트 패턴 |
|---:|---|---|---|---|
| 1 | CR01 | C | 60 64 67 | 공통 패턴 |
| 2 | CR02 | Cm | 60 63 67 | 공통 패턴 |
| 3 | CR03 | F | 65 69 72 | 공통 패턴 |
| 4 | CR06 | Fm | 65 68 72 | 공통 패턴 |
| 5 | CR05 | G | 67 71 74 | 공통 패턴 |
| 6 | CR04 | Gm | 67 70 74 | 공통 패턴 |
| 7 | CR08 | Fm | 65 68 72 | 공통 패턴 |
| 8 | CR07 | C | 60 64 67 | 마지막 화음 길게 |

공통 패턴: root 파트는 박0·2에서 길이1.4박, third 파트는 박1·3에서 길이0.8박, fifth 파트는 박0.5·1.5·2.5·3.5에서 길이0.3박. 박은 마디 시작 0 기준이다. 마지막 마디는 세 음을 박0에 길이3.5박으로 함께 연주한다. 모든 note gate와 release는 다음 마디 화음 변경 전 끝나도록 한다. 예를 들어 마지막 fifth는 3.5+0.3박에 gate가 끝나며 0.12초 release를 더해 3.96박에 종료한다. 80 BPM에서 마디 끝까지 30ms 여유가 있다. 템포를 후속에서 바꿀 때는 `gateEnd + releaseSeconds <= nextBarStart - 0.01`을 다시 검사하고 필요하면 gate를 줄인다.

`파트별 듣기`, `전체 듣기`, `정지`를 제공한다. 합주는 자동 반복하지 않는다. 각 마디 화음 이름과 참여한 주문 악기를 표시하되 터치 과제를 삽입하지 않는다. 사용자는 시간 제한 없이 같은 화음의 역할을 하나씩 들을 수 있다. 외형은 8악기가 함께 무대에 있지만 한 시점의 화성은 해당 마디의 음만 사용한다.

## 12 학습 성취와 전이 검증

### 12.1 세 종류의 결과

1. **플레이 성취**: 주문 8개를 최종적으로 수리했는가. 도움 사용 가능.
2. **개념 확인**: 근음·3음·5음, 장·단의 간격을 안내 없이 설명·선택했는가.
3. **전이**: 게임과 다른 음역·근음·표현·악기에서 같은 관계를 사용할 수 있는가.

이 세 결과를 합친 “음악 실력 92점”은 만들지 않는다. 정답 누르기, 한 번 맞힌 것, 반복하여 외운 것만으로 이해·기억·악기 연주 향상을 주장하지 않는다.

### 12.2 MVP 내 개인 확인

- CR05~CR08의 첫 제출 정오와 최대 도움 수준을 기록한다.
- 동일 주문을 다시 풀 때는 `연습 재시도`로 표시하며 처음 시도와 덮어쓰지 않는다.
- 개념 확인 질문은 수리와 별도 record다. 정답 설명을 본 다음 답한 문항은 독립 성취로 세지 않는다.
- 첫 완료 후 `다른 모양으로 확인하기`는 선택 항목이다. 수리 게임과 다른 음 버튼 배열로 C/F/G의 3음을 구성하게 한다.
- 접근성 옵션·큰 음 버튼·스크린리더 사용은 힌트로 간주하지 않는다. 목표 관계나 정답을 공개하는 도움만 힌트다.

관계 확인 UI는 `question → explanation` 두 단계다. 독립 확인을 기록하려면 첫 답변 전에 변경 역할·정답 간격을 직접 공개하는 해설을 숨긴다. 사용자가 `해설 먼저 보기`를 누르면 즉시 보여 주되 `answerRevealedBeforeFirstAnswer=true`로 저장한다. 튜토리얼에서 이미 해당 답을 직접 보여 주었다면 같은 플래그를 세운다. 도움·해설을 본 즉시 확인은 연습 기록이며 독립 평가가 아니다. 오답이나 건너뛰기도 수리 완료와 합주 해금을 막지 않는다.

### 12.3 출시 전 소규모 연구 계획

**사용성 조사**와 **교육효과 연구**를 구분한다. 초기 6~8명 정도의 입문자 관찰은 조작 오류·이해의 장애를 찾기 위한 제안 규모다. 이 정도 표본으로 일반적인 교육효과를 주장하지 않는다. 연령대가 확정되면 해당 집단을 별도로 모집하고 숙련자 결과와 섞지 않는다.

교육효과를 평가하려면 연구 담당자가 사전 능력, 목표 효과 크기, 분석 방법을 정하고 필요한 표본 수를 별도 산정한다. 가능하면 같은 개념을 같은 시간 학습하는 비게임 비교 조건을 두고 무작위 배정한다. 게임군만 전후 측정한 결과는 연습 효과·문항 기억·기기 익숙해짐과 분리하기 어렵다는 한계를 보고한다.

### 12.4 독립 평가 구성

| 평가 | 문항 예 | 측정하려는 것 | 답/채점 |
|---|---|---|---|
| 역할 식별 | C4 E4 G4에서 근음과 3음 지목 | 용어와 음의 연결 | C4와 E4, 각 1점 |
| 간격 설명 | 장·단3화음의 근음→3음 간격 | 관계 기억 | 4·3반음, 각 1점 |
| 익숙한 근음의 새 배치 | E4 G4 C5를 보여 주고 “C의 음 모음인가?” | 음고류 보존 인식 | 예, C E G라 설명 |
| 새 근음 구성 | A3를 근음으로 단3화음을 음 타일로 만들기 | 규칙의 근전이 | A3 C4 E4 |
| 수리 불필요 구별 | A3 C4 E4가 A단3화음 주문에 맞는지 확인 | 무조건 한 음을 바꾸는 전략 구별 | 그대로 정답, 수정 불필요 |
| 새 근음 구성 | D4 장3화음 만들기, 반음표 제공 여부 기록 | 샤프를 포함한 전이 | D4 F♯4 A4 |
| 청각 비교 | 같은 근음·음색의 장/단 2개, 어느 3음이 더 높은지 | 소리와 변화 연결 | 장3화음 쪽, 순서 균형화 |
| 실제/다른 가상 악기 | 지정된 근음에서 장→단으로 바꾸기 | 표현·도구 간 전이 | 3음만 반음 낮춤, 운지 별도 |

전위 이름을 아직 가르치지 않은 MVP에서 E4–G4–C5의 “제1전위” 용어를 요구하지 않는다. 배치 보존 인식은 탐색적 전이 결과로 보고하며 기본 학습목표 통과율에 넣지 않는다. 실제 악기 과제도 연주 기술이 다른 변수가 되므로 올바른 음 선택과 운지를 나누어 관찰한다. 게임 밖 반주나 다른 악기로의 적용은 음악 영역 안의 더 먼 전이다. 집중력·지능·일반 학업 능력 등 음악 밖 원전이 향상은 이 설계로 주장하지 않는다. 오선을 읽는 법을 가르치지 않았다면 독보 실패를 화음 이해 실패로 해석하지 않는다.

### 12.5 평가 운영과 반례

- 사전/사후/가능하면 7~14일 지연 평가를 제안한다. 지연 평가는 사용자에게 자동으로 의무화하거나 동의 없이 연락하지 않는다.
- 평행 문항 세트 A/B를 교차 배정하고 동일 정답 순서를 반복하지 않는다. 새 근음 문항의 선행지식 부담을 기록한다.
- 평가 중 즉시 정답 피드백을 끄고, 완료 뒤 해설을 제공한다.
- 앱 평가 화면이 교육 연습으로 노출된 뒤에는 같은 문항을 독립 전이 검사에 재사용하지 않는다.
- 사전 점수가 이미 높은 사람의 천장 효과, 무음 모드, 청각 보조기기, 익숙한 악기 경험을 기록하되 민감정보를 불필요하게 수집하지 않는다.
- “C장화음은 E가 들어간다”는 문장만 외운 경우 F/G 전이에서 드러난다. “단화음은 검은건반 하나”라는 오개념은 A단3화음 예로 점검한다.
- “가운데 음=3음” 오개념은 후속 전위/넓은 배치에서 점검한다. MVP에서는 이를 정설처럼 가르치지 않는 것이 우선이다.

### 12.6 제품 의사결정 지표

검증 목표 초안: 첫 사용자의 80% 이상이 도움 없이 음 교체 동작을 수행, 참가자의 80% 이상이 `원래/현재/목표`를 혼동하지 않음, CR07에서 가운데 음만 반복 변경하는 사례가 낮아짐. 이 수치는 연구 근거가 있는 기준이 아니라 다음 설계 수정 여부를 결정하기 위한 내부 목표다. 소표본에서는 분모와 개별 사례를 함께 보고한다.

학습 효과 수치는 실제 수집 전 공란으로 둔다. 목표를 못 채우면 캐릭터·보상 양을 늘리기 전에 용어, 음 선택 도구, 비교 조건, 안내 제거 시점을 조정한다.

## 13 프런트엔드 구조

### 13.1 권장 구현 스택

정적 배포 가능한 TypeScript + React + Vite, DOM/SVG UI, Web Audio, IndexedDB를 권장한다. 첫 구현에는 게임엔진·3D·서버·LLM 런타임을 넣지 않는다. 음악 규칙은 UI와 분리된 순수 TypeScript로 작성한다. 버전은 구현 시작 시 공식 안정 릴리스를 확인하고 lockfile에 고정한다. 문서의 기술 확인일이 이후의 최신 버전을 보장하지 않는다. [Vite 공식 안내](https://vite.dev/guide/), [React effect 규칙](https://react.dev/reference/react/useEffect)

React 개발 모드에서 effect가 추가 setup/cleanup을 실행할 수 있으므로 컴포넌트 마운트마다 AudioContext를 생성하지 않는다. 사용자 입력에서 구동되는 단일 AudioService를 두고 listener/timer/voice의 정리 함수를 반드시 제공한다. 음악 판정을 effect 안에서 부수효과와 섞어 두 번 제출하는 구조를 피한다.

### 13.2 디렉터리 계약

```text
src/
  app/                 앱 시작, 라우트, 오류 경계, 의존성 연결
  domain/music/        음 표기, interval, chord, voicing, grade
  domain/session/      상태 전이, revision, attempt, hint
  content/             주문 JSON, 한국어 문구, 합주 데이터
  audio/               AudioService, voice, scheduler, transport
  persistence/         IndexedDB, migration, import/export, recovery
  ui/screens/          시작, 목록, 작업대, 결과, 합주, 설정
  ui/components/       NoteSlot, Piano, NotePad, OrderCard, Feedback
  accessibility/       focus, announcements, preferences
  diagnostics/         로컬 성능·오류 진단, 개발 전용
tests/
  unit/ fixtures/ integration/ e2e/ audio/ accessibility/
public/
  assets/              해시된 자체 제작 자산
  licenses/            자산·코드 라이선스 장부
```

의존 방향은 UI→세션→음악 도메인이다. 도메인은 DOM·AudioContext·IndexedDB·React를 import하지 않는다. AudioService는 NoteEvent만 받으며 “정답인지”를 알지 못한다. 저장 계층은 직렬화된 도메인 snapshot만 받는다. 콘텐츠의 display text가 정답 계산에 사용되어서는 안 된다.

### 13.3 핵심 인터페이스

```ts
type Letter = "C" | "D" | "E" | "F" | "G" | "A" | "B";
type Role = "root" | "third" | "fifth";
type Quality = "major" | "minor";
type SpelledPitch = { letter: Letter; accidental: -2|-1|0|1|2; octave: number };
type ChordTarget = {
  root: SpelledPitch;
  quality: Quality;
  requiredMidi: readonly [number, number, number];
  requiredSpelling: readonly [SpelledPitch, SpelledPitch, SpelledPitch];
  registerMode: "exact" | "pitch-class";
  inversion: 0 | 1 | 2 | null;
  spellingRequired: boolean;
};
type VoiceSlot = { id: string; pitch: SpelledPitch | null };
type Grade = {
  status: "invalid" | "incomplete" | "incorrect" | "correct";
  codes: readonly string[];
  pitchClassCorrect: boolean;
  spellingCorrect: boolean;
  registerCorrect: boolean;
  inversionCorrect: boolean;
  mismatchedRoles: readonly Role[];
};
type NoteEvent = { midi: number; at: number; duration: number; timbre: string; gain: number };
```

`VoiceSlot.id`는 물리 부품 ID다. 슬롯 이름 자체를 항상 화음 역할로 사용하지 않는다. 처음 화면의 역할 배지는 현재 음이 목표 구성음과 어떻게 대응되는지에서 구한다. 특정 역할이 맞지 않으면 `3음 자리`처럼 슬롯 기능을 설명하고 “이 음이 올바른 3음”이라고 확정하지 않는다.

`inversionCorrect`는 구성음과 최저음이 유효할 때만 의미가 있다. 구성음이 틀렸다면 false와 `MEMBERS_MISMATCH`를 반환하고 잘못된 전위명을 생성하지 않는다. 향후 중복음을 지원할 때는 최소 한 개씩 구성음 존재 여부와 허용 중복 정책을 별도로 정의한다.

### 13.4 음정 계산 계약

장·단3화음 생성은 근음 문자를 +2, +4 단계 진행하여 3음·5음의 문자 이름을 먼저 정하고 반음 목표에 맞는 변화표를 계산한다. MIDI 간격만 더한 뒤 전역 `sharpNames` 표로 이름을 붙이지 않는다. E♭–G–B♭ 같은 확장이 이 원칙으로 정확해진다.

음정 표시 함수는 두 값 `(diatonicNumber, semitoneDistance)`를 함께 받는다. C–D♯의 3반음과 C–E♭의 3반음을 모두 “단3도”라고 하지 않는다. C–D♯는 문자 기준 2도에 해당한다. MVP는 입력을 문맥 철자로 정규화하지만 일반 함수 테스트에서는 이런 차이를 검사한다.

## 14 상태 머신과 이벤트

### 14.1 서로 분리되는 상태 축

| 축 | 상태 |
|---|---|
| 앱 | boot, ready, contentError, recovery |
| 학습 세션 | orderIntro, editing, checking, feedback, reflection, completed |
| 오디오 | locked, preparing, ready, playing, paused, unavailable |
| 저장 | clean, dirty, saving, failed, memoryOnly |
| 화면 | home, orders, workbench, ensemble, sandbox, settings |

`playing`을 학습 세션 전체 상태로 삼지 않는다. 음을 듣는 동안에도 주문과 도움을 볼 수 있다. 데이터 변경을 허용한 동작은 재생 snapshot을 취소한 뒤 새 revision을 만든다.

### 14.2 전이 표

| 현재 | 이벤트 | 검사 | 다음과 부수효과 |
|---|---|---|---|
| boot | LOAD_OK | 콘텐츠·저장 schema 유효 | ready, 마지막 화면 복원 |
| boot | SAVE_INVALID | 복구 가능한 백업 존재 | recovery, 사용자 선택 |
| orderIntro | START_ORDER | 주문 ID 유효 | editing, 원래 음 복제 |
| editing | SELECT_SLOT | 편집 가능한 ID | editing, 포커스 이동 |
| editing | SELECT_PITCH | 허용 음역·잠금 확인 | revision+1, undo push, 오디오 취소, dirty |
| editing | CHECK | 최신 revision, 세 음 존재 | checking, 순수 grade 계산 |
| checking | GRADE_READY | orderId·attemptId·revision·submissionId가 모두 현재 요청과 같음 | feedback 또는 reflection |
| checking | GRADE_READY | 네 식별값 중 하나라도 다름 | 결과 폐기 |
| feedback | EDIT | 없음 | editing, 오류 강조 해제 |
| reflection | ANSWER | 문항 ID 유효, 첫 답변 여부 | 개념 결과 기록, explanation 단계 |
| reflection | SHOW_EXPLANATION | 첫 답변 전이면 노출 플래그 기록 | explanation 단계, 저장 |
| reflection | SKIP | 없음 | 평가 skipped, explanation 단계 |
| reflection | CONTINUE | 수리 정답 | completed, 완료 커밋 |
| completed | NEXT | 다음 ID 존재 | orderIntro |
| 임의 화면 | HIDDEN | 없음 | 재생 취소, 저장 시도, 세션 유지 |
| 임의 화면 | RETURN | 없음 | 자동 재생 없이 화면 복원 |

`CHECK`는 동기 순수 함수라도 중복 클릭 보호를 위한 `submissionId`를 갖는다. 판정 요청과 응답에는 `{orderId, attemptId, revision, submissionId}`를 모두 포함하고 활성 요청과 완전히 일치할 때만 반영한다. 다른 주문에서 revision 숫자가 같아도 이전 결과는 적용되지 않는다. 중복 제출은 기존 결과를 반환한다. 새 주문과 명시적인 새 연습마다 새 attemptId를 발급한다. 단순 새로고침·복귀는 기존 attemptId를 유지한다. 완료 저장 역시 `{orderId, contentVersion, completionId}`로 멱등 처리한다. 새 주문을 열었는데 이전 주문의 타이머가 완료 화면을 띄우는 일이 없어야 한다.

### 14.3 되돌리기와 시범

undo는 음 배열·선택 슬롯만 복원하고 도움 사용 기록·첫 제출 정오를 되돌리지 않는다. 시범을 보기 전 상태를 별도 snapshot으로 보관한다. 시범 상태에서 바로 완료해도 결과는 assisted다. `원래대로`는 시작 화음을 복원하지만 새 독립 시도가 자동 생성되는 것은 아니다. 처음부터 새 연습을 원하면 완료 화면의 `다시 연습`으로 새 attemptId를 만든다.

## 15 콘텐츠 스키마와 정답 데이터

### 15.1 주문 스키마의 필수 필드

```ts
type Order = {
  schemaVersion: 1;
  contentVersion: string;
  id: string;
  title: string;
  root: SpelledPitch;
  quality: Quality;
  initial: readonly [SpelledPitch, SpelledPitch, SpelledPitch];
  target: readonly [SpelledPitch, SpelledPitch, SpelledPitch];
  initialMidi: readonly [number, number, number];
  targetMidi: readonly [number, number, number];
  editableSlots: readonly number[];
  allowedMidi: readonly [number, number];
  displaySpellingMap: Readonly<Record<number, SpelledPitch>>;
  registerMode: "exact";
  spellingRequired: false;
  inversion: 0;
  primaryConcept: "major-third" | "minor-third" | "fifth" | "root";
  hintPolicy: "guided" | "optional";
  reflection: { prompt: string; options: readonly string[]; answerIndex: number };
};
```

JSON loader는 추가/누락 필드, tuple 길이, MIDI 범위, 문자열 길이, 올바른 enum을 검사한다. targetMidi를 신뢰해서 음이름을 덮어쓰지 않고 표기에서 계산한 MIDI와 반드시 대조한다. target는 root+quality로 계산한 화음과 동일해야 한다. 양쪽 값이 다르면 빌드를 실패시킨다. UI가 문자열을 HTML로 렌더링하지 않는다. `displaySpellingMap`은 허용 범위의 모든 MIDI 키를 정확히 한 번 포함하고 각 표기의 계산값이 키와 같아야 한다. 목표 구성음의 문맥 철자는 이 map보다 우선한다. map은 오답 음의 일관된 표시용이며 정답 계산에 사용하지 않는다.

### 15.2 스키마 운영 규칙

- `schemaVersion`은 저장/데이터 형식, `contentVersion`은 정답·문항·안내의 묶음 버전이다.
- 오탈자 수정만이라도 배포 버전을 남긴다. 정답·학습목표 변경은 기존 평가 결과와 합산하지 않는다.
- 음 배열 순서는 실제 슬롯 순서다. 판정은 필요한 조건에 따라 다중집합·최저음·정확 음역을 사용한다.
- 수정 가능한 슬롯 수가 0이거나 정답으로 이동할 수 없는 콘텐츠는 validator가 거절한다.
- CR01~CR02는 초기/목표의 잠긴 슬롯이 같아야 한다. 모든 시작값은 정답과 달라야 한다.
- 학습 주문 수는 8로 유지한다. 전이 평가 fixtures와 후속 전위 예시는 별도 namespace에 둔다.

아래 부록 A는 전체 8주문의 기계가 읽을 수 있는 기준 데이터다. 실제 구현은 이를 JSON 파일로 분리하고 이 문서와 데이터 파일을 함께 버전 관리한다.

## 16 저장과 복구

### 16.1 저장 범위

IndexedDB를 기본으로 쓰고 설정도 같은 DB에 저장한다. DB 이름 `chord-repair-shop`, 버전 1. 다른 게임의 저장 키를 재사용하지 않는다. IndexedDB는 구조화된 데이터를 비동기 저장하는 브라우저 API다. 브라우저 데이터는 용량 제한·삭제·비공개 모드 등에 의해 없어질 수 있으므로 영구 보장을 하지 않는다. [MDN IndexedDB](https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API), [저장 용량 및 제거 정책](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)

| store | key | 내용 |
|---|---|---|
| meta | profile | schemaVersion, contentVersion, revision, updatedAt |
| settings | main | 음량, mute, 표기, 입력 모드, reducedMotion |
| attempts | attemptId | orderId, 최초 제출, 도움, 최종 음, 개념 결과 |
| progress | orderId | 완료 여부, 완료 contentVersion, 최근 attemptId |
| draft | active | orderId·attemptId·contentVersion·revision, 세 음·선택 슬롯, 세션/질문 단계, 최대 도움, 첫 제출 결과, 개념 첫 답변, 해설 노출, completionId |
| backup | previous | 직전 정상 draft와 진행 요약 |

계정·이름·생년월일·마이크·위치·연락처는 수집하지 않는다. 기본 analytics 네트워크 전송은 없다. 진단 정보는 로컬에서 보고 사용자가 내보내기를 선택해야 파일이 만들어진다.

### 16.2 저장 시점

- 음 변경 후 300ms debounce, 최대 1초 안에 최신 draft 저장.
- HINT, CHECK, ANSWER, SHOW_EXPLANATION, SKIP 이벤트에서는 변경된 attempt 증거와 draft를 즉시 transaction으로 저장한다. 노출 플래그는 한 번 true가 되면 같은 attempt에서 false로 돌아가지 않는다. 최초 제출 정오도 이후 시도로 덮어쓰지 않는다.
- 주문 완료는 progress와 attempt 저장 및 해당 draft 정리를 같은 transaction에서 커밋한다. 완료 UI는 저장 성공 여부를 별도 표시하되 저장 실패 때문에 수리를 취소하지 않는다.
- 설정 변경도 debounce하며 화면 종료 시 추가 flush를 시도한다. pagehide 저장만 믿지 않는다.
- 체크포인트 revision과 실제 저장 revision을 비교한다. 낮은 revision이 늦게 도착해 최신 값을 덮어쓰지 못하게 한다.
- 모든 transaction 오류를 처리한다. 미처리 Promise가 앱 전체를 중단하면 안 된다.

### 16.3 중단과 손상 복구

시작 시 현재 데이터 검증 → 최신 정상 snapshot 검사 → 필요한 migration 실행 → 원자적 교체 순서다. 중단 시도는 동일 attemptId와 도움·첫 제출·해설 노출 상태를 복원한다. 증거 필드가 빠진 구버전이나 저장 실패 복구에서는 독립 성취를 추정하지 않고 `evidenceStatus=unknown`으로 둔다. 손상된 데이터를 발견했다고 전체 DB를 바로 삭제하지 않는다. 사용자는 `이전 정상 기록 사용`, `현재 기록 내보내기`, `새로 시작`을 고를 수 있다. 새로 시작은 이 앱의 학습 기록만 삭제한다는 범위를 확인하고 실행한다.

저장 공간 부족/권한 불가이면 memoryOnly로 전환한다. 상단에 지속적인 작은 경고와 내보내기 버튼을 제공한다. 이 상태에서 브라우저를 닫으면 잃을 수 있다는 사실을 한 번 분명히 알린다. 자동으로 영구 저장 권한을 요청하지 않는다.

### 16.4 내보내기와 가져오기

내보내기 형식 `chord-repair-progress-v1.json`, 최대 256KB. schemaVersion, contentVersion, 진행·설정·시도 요약만 담고 오디오 버퍼·디바이스 식별자는 포함하지 않는다. 가져오기는 JSON.parse 후 엄격 검증하고 프로토타입 키·과대 배열·지원하지 않는 버전을 거절한다. 사용자가 확인하면 현재 기록을 백업한 뒤 **교체**한다. MVP에서 자동 병합은 하지 않는다.

두 탭이 동시에 열리면 BroadcastChannel 지원 시 활성 편집 탭을 알리고 다른 탭을 읽기 전용으로 전환한다. 지원하지 않으면 transaction 내 revision 충돌을 감지해 덮어쓰기를 막고 새로고침/내보내기를 제안한다. 존재하지 않는 탭의 영구 잠금이 남지 않도록 잠금에는 만료와 명시적 인수 절차를 둔다.

## 17 테스트와 수용 기준

### 17.1 자동 테스트 층

순수 함수·콘텐츠는 Vitest 등으로, 사용자 흐름은 Playwright로 검사할 수 있다. 모바일 에뮬레이션은 화면과 입력 조건 확인에는 도움이 되지만 iPhone 실제 오디오·백그라운드·Bluetooth 동작을 대체하지 않는다. [Vitest 공식 안내](https://vitest.dev/guide/), [Playwright 에뮬레이션](https://playwright.dev/docs/emulation)

| 층 | 필수 검사 | 통과 기준 |
|---|---|---|
| 음악 unit | 음 표기, 반음, chord 생성, 전위 | 모든 fixture 일치 |
| 콘텐츠 unit | 8주문 스키마·도달성·정답 | 오류 0, 각 시작은 오답 |
| reducer unit | revision, undo, stale 결과, 힌트 | 불가능한 전이 거절 |
| 오디오 unit | 주파수, envelope, cancel generation | 예약·중단 계약 일치 |
| 통합 | 수정→제출→결과→저장→복원 | 최종 revision 일치 |
| E2E | 8주문, 무음, 뒤로, 새로고침 | 진행 손실·중복 완료 없음 |
| 접근성 | 키보드·스크린리더·대비·확대 | 핵심 흐름 차단 0 |
| 실제 기기 | unlock, 장치 전환, 잠금·복귀 | 갑작스러운 자동 재생 없음 |

### 17.2 음악 검증 fixture

| 입력/조건 | 기대 |
|---|---|
| C4, E♭4, G4 → C major exact | THIRD_MISMATCH |
| C4, E4, G4 → C major exact | CORRECT |
| C4, E♭4, G4 → C minor exact | CORRECT |
| C4, E4, E4 → C major | 5음 누락, 정답 아님 |
| E4, G4, C5 → C major pitch-class, any inversion | 화음 정체성 정답 |
| E4, G4, C5 → C major inversion 1 | 정답 |
| E4, G4, C5 → C major inversion 0 | INVERSION_MISMATCH |
| C4, G4, E5 → C major inversion 0, pitch-class | 정답, 넓은 배치 |
| C3, E3, G3 → C4 E4 G4 exact | REGISTER_MISMATCH |
| C4, D♯4, G4 → C minor, spellingRequired=true | SPELLING_MISMATCH |
| B♯3와 C4 | MIDI 60으로 같음, 철자는 다름 |
| C♭4와 B3 | MIDI 59로 같음, 철자는 다름 |
| F4 A♭4 C5 | F minor, root 65, 3반음·7반음 |
| G4 B♭4 D5 | G minor, root 67, 3반음·7반음 |

전체 12근음으로 일반화 테스트를 하더라도 MVP가 12근음을 교육한다고 표시하지 않는다. 지원하지 않는 이중변화표를 생성해야 하는 확장 조건에서는 조용히 다른 철자로 바꾸지 말고 명시적 unsupported 또는 정확한 표기로 처리한다.

### 17.3 실패 시나리오 테스트

1. 전후 비교를 10회 빠르게 누른다. 마지막 요청만 들리고 voice 수가 상한을 넘지 않는다.
2. 비교 1번째 화음 도중 음을 바꾼다. 오래된 2번째 화음과 새 화면이 엇갈리지 않는다.
3. 제출 직후 다른 주문으로 이동한다. 이전 결과가 새 주문을 완료하지 않는다.
4. 소리가 시작되기 전 뒤로 간다. 예약 노드가 나중에 소리를 내지 않는다.
5. 큰 음 버튼을 탭한 채 세로 스크롤한다. 뜻하지 않은 음 교체가 없거나 즉시 되돌릴 수 있다.
6. 활성 pointer 중 창을 잃는다. 소리가 무한 유지되지 않는다.
7. 저장 실패를 강제한다. 작업은 계속되고 완료가 사라졌다고 오해시키지 않는다.
8. draft JSON 일부를 손상시킨다. 이전 정상 복구를 제안하고 자동 삭제하지 않는다.
9. 구버전·미래 버전 저장을 가져온다. 안전한 migration 또는 구체적인 거절을 한다.
10. 한 주문을 두 탭에서 수정한다. revision 충돌로 오래된 저장을 막는다.
11. 설정에서 글자 크기/모션/음소거를 바꾼다. 진행 상태와 판정이 바뀌지 않는다.
12. 200%/400% 확대와 가로 회전 후 되돌린다. 주요 버튼이 잘리거나 겹치지 않는다.

### 17.4 실제 기기 검사표

출시 시점의 iOS Safari 최신 안정판과 지원할 직전 주요 버전, Android Chrome 최신 안정판, 데스크톱 Chrome·Safari·Firefox를 대상으로 한다. 정확한 OS/브라우저 버전·기기 모델·유선/내장/Bluetooth 출력을 검수표에 적는다. 최소 지원 버전은 실제 검증 후 출시 노트에 고정한다. 문서에서 미검증 버전을 지원한다고 약속하지 않는다.

- 작은 iPhone급 세로 화면, 중급 Android, 320px 좁은 viewport.
- 저전력 모드, 네트워크 끊김, 화면 잠금, 전화/미디어 중단, 앱 전환 30초 후 복귀.
- VoiceOver, TalkBack, 키보드만 사용, reduced motion, 시스템 큰 글자.
- 내장 스피커에서 C/Cm·F/Fm·G/Gm 전후 음의 존재가 확인되는지 청감 검사. 이것은 사용자의 장단 식별 능력 시험과 다르다.
- 브라우저 음소거·시스템 음량 0·autoplay lock을 구별해 잘못된 성공 표시를 하지 않는지 검사.

## 18 성능 예산과 운영 기준

모든 수치는 첫 구현의 검증 목표다. 측정 전 달성했다고 주장하지 않는다.

| 항목 | 초기 목표 | 측정 조건 |
|---|---:|---|
| 초기 JS | gzip 250KB 이하 | production build |
| 초기 전체 전송 | 1.5MB 이하 | 핵심 작업대까지, 폰트 포함 |
| 전체 MVP 자산 | 5MB 이하 | 합주·장식 포함 |

성능이 나쁘면 장식 애니메이션→그림 크기→동시 음색 수 순으로 줄인다. 판정 정확도·접근성·저장 복구를 삭제하지 않는다. 처음에는 시스템 글꼴을 사용하고 별도 음악 기호 폰트는 필요한 글리프만 포함한다. 로컬 데이터는 최근 상세 시도 100개를 유지하고 오래된 기록은 주문별 요약으로 압축한다. 첫 시도·도움 여부·최근 성취를 보존한다.

## 19 개인정보와 보안 및 권리

### 19.1 최소 수집 원칙

MVP에는 로그인, 소셜 공유, 광고 SDK, 추적 쿠키, 서버 학습 기록 전송이 없다. 작업은 기기 내에서 이루어진다. 이 설계가 모든 개인정보 규제를 자동 충족한다는 뜻은 아니다. 실제 배포 지역·대상 나이·분석 도구가 정해지면 적용 기준을 별도로 검토한다.

연구 참여자에게 수집 목적·항목·보관 기간·철회 방법을 설명하고 동의를 받는다. 미성년자를 대상으로 하게 되면 필요한 보호자 절차를 먼저 확정한다. 사용성 녹화·음성·실명은 기본 수집하지 않으며 필요 시 별도 동의를 받는다. 게임을 이용하려고 연구 참여를 강제하지 않는다.

### 19.2 구현 보안

- 정적 콘텐츠와 로컬 import를 엄격 검증한다. 외부 HTML, 임의 스크립트, 악성 파일 URL을 실행하지 않는다.
- 콘텐츠는 build에 포함하고 첫 버전에서 원격 임의 JSON 실행을 지원하지 않는다.
- CSP를 적용하고 필요한 origin만 허용한다. 마이크·카메라·위치 권한을 요청하지 않는다.
- local import 크기와 배열 길이 상한을 적용한다. 오류 로그에 전체 학습 기록이나 사용자 파일을 전송하지 않는다.
- 의존성과 자산의 출처·버전·라이선스를 lockfile 및 장부로 관리한다.
- 분석·계정·클라우드 동기화 추가는 별도의 개인정보·보안 검토를 통과한 후속 기능이다.

### 19.3 저작권과 이름

화음 관계 자체를 설명하는 콘텐츠와 원작 합성 음형을 사용한다. 기존 게임의 녹음·악보 편곡·캐릭터·스크린샷·효과음은 허락 없이 재사용하지 않는다. 음악의 음표가 단순해도 특정 녹음과 시각 자산의 권리는 별도로 확인해야 한다. 외주 음원은 상업적 웹 배포·수정·샘플 재생·재배포 허용 범위를 문서로 확보한다. 상표·법률 판단은 출시 전 담당자의 확인 항목이며 이 문서는 법률 의견서가 아니다.

## 21 오프라인과 배포 확장

MVP는 한 번 로드한 세션에서 네트워크가 끊겨도 수리를 계속할 수 있도록 필수 콘텐츠·합성 코드를 메모리에 가진다. 브라우저를 닫았다가 오프라인으로 다시 열기까지 보장하는 기능은 별도 PWA 단계다.

Service Worker를 추가한다면 HTTPS, 설치·활성화 수명주기, 캐시 버전·업데이트 정책을 따른다. 오래된 코드와 새 콘텐츠를 섞지 않도록 앱·콘텐츠·자산 manifest를 한 releaseId에 묶는다. 새 버전은 진행 중 강제 적용하지 않고 시작 화면에서 저장 후 활성화한다. [MDN Service Worker 사용 안내](https://developer.mozilla.org/en-US/docs/Web/API/Service_Worker_API/Using_Service_Workers)

오프라인 캐시는 진행 저장과 별개다. 캐시 삭제가 progress를 의도적으로 삭제해서는 안 된다. 캐시 용량 부족이면 온라인 사용으로 낮추고, 앱 전체가 쓸 수 없게 만들지 않는다. 서버 동기화·푸시 알림·설치 유도는 첫 MVP 범위가 아니다.

## 22 후속 학습 확장

### 22.1 첫 확장은 전위

조건: MVP에서 역할·장단 간격을 설명할 수 있고, 실제 사용성 문제가 해결된 뒤 진행한다. 목표는 “근음은 항상 가장 낮은 음” 오개념을 교정하고 동일 구성음의 다른 배치를 인식하는 것이다.

| ID | 과제 | 입력 또는 시작 | 허용 정답 | 주의 |
|---|---|---|---|---|
| INV01 | C화음인지 구별 | C4 E4 G4 / E4 G4 C5 | 둘 다 C 장3화음 | 전위 이름은 해설로 도입 |
| INV02 | C 장3화음 제1전위 만들기 | C4 E4 G4 | E4 G4 C5 | 최저음 E, 근음 C 유지 |
| INV03 | C 장3화음 제2전위 만들기 | C4 E4 G4 | G3 C4 E4 또는 지정 음역의 G4 C5 E5 | 허용 음역 조건을 과제에 명시 |
| INV04 | 넓은 배치 분류 | C4 G4 E5 | 기본 위치 | 화면 가운데를 3음으로 고정하지 않음 |
| INV05 | Fm 제1전위 구별 | A♭3 C4 F4 | Fm/A♭ | A♭가 근음으로 바뀐 것이 아님 |
| INV06 | Gm 제2전위 구별 | D4 G4 B♭4 | Gm/D | 최저음은 5음 |

후속에서는 슬롯 역할을 고정하지 않고 임의 voice 3개로 입력한다. rootPitchClass·quality·allowedRange·requiredBassRole로 판정하며 여러 정답을 허용한다. 어느 정답이 “더 좋은 성부 진행”인지는 별도 목표 없이 판정하지 않는다.

### 22.2 그다음 확장 순서

1. D/A/E 등 새로운 근음과 샤프·플랫 철자.
2. 기본 위치·전위·넓은 배치 비교.
3. 한 조성 안의 I·IV·V와 실제 짧은 진행. `C화음`과 `C장조`를 명확히 구분.
4. 감·증3화음, 7화음은 별도 주문과 음정 설명을 설계.
5. 실제 MIDI 입력은 지원 기기·권한·접근성·이벤트 지연을 별도로 검증한 후 도입.
6. 실제 마이크 다성 인식은 음악 인식 정확도·소음·개인정보·기기 편차를 검증하는 별도 프로젝트로 둔다.

후속 기능을 위해 MVP에 빈 메뉴·결제 유도·잠금 자물쇠를 과하게 노출하지 않는다. 완성된 8주문만으로 작은 독립적인 경험이 끝나야 한다.

## 24 최종 개발 완료 체크리스트

- [ ] 8주문의 시작음·목표음·MIDI·질문 정답이 부록 A와 일치한다.
- [ ] CR01에서 C4–E♭4–G4를 E4 교체로 수리하고 실제 소리가 바뀐다.
- [ ] 장·단 관계, 근음·3음·5음, 전위·옥타브·철자를 혼동하지 않는다.
- [ ] 정답 키 상시 점멸·시간압박·수정 횟수 감점이 없다.
- [ ] 모든 핵심 동작을 탭·큰 음 버튼·키보드로 수행할 수 있다.
- [ ] 전후 비교는 동일 음색·음량·음역·길이 조건이다.
- [ ] 오디오 unlock·중단·복귀·취소·폭주가 실제 기기에서 검증되었다.
- [ ] 페이지 새로고침·저장 실패·손상·구버전·두탭 충돌 복구가 검증되었다.
- [ ] 도움 사용·플레이 완료·독립 개념 확인·청음 평가가 분리된다.
- [ ] 합주에 서로 모순되는 장·단 화음을 동시에 무작정 합치지 않는다.
- [ ] 접근성·성능·권리·개인정보 검수를 통과했다.

```ts
describe("첫 수리의 계약", () => {
  it("C단3화음은 C장3화음 주문에서 3음 불일치다", () => {
    const result = grade([p("C4"), p("Eb4"), p("G4")], target("C4", "major"));
    expect(result.status).toBe("incorrect");
    expect(result.codes).toContain("THIRD_MISMATCH");
  });
  it("정답은 수정 경로와 무관하다", () => {
    expect(grade([p("C4"), p("E4"), p("G4")], target("C4", "major")).status)
      .toBe("correct");
  });
  it("건반의 D#와 Eb는 같은 음고 입력이다", () => {
    expect(toMidi(p("D#4"))).toBe(toMidi(p("Eb4")));
    expect(spellForTask(63, p("C4"), "minor")).toEqual(p("Eb4"));
  });
  it("정규 철자 검사는 음고 검사와 다르다", () => {
    const t = { ...target("C4", "minor"), spellingRequired: true };
    expect(grade([p("C4"), p("D#4"), p("G4")], t).codes)
      .toContain("SPELLING_MISMATCH");
  });
});
```

이 예시는 계약 설명용이며 저장소에 이미 실행된 테스트 코드가 아니다. 실제 테스트에서는 순수 함수, 콘텐츠 validator, DOM 입력, 실제 오디오를 각각 검증한다. mock AudioContext 테스트를 통과한 것만으로 사용자가 소리를 들었다고 판단하지 않는다.

## 부록 D 이 설계 문서의 검증 범위

작성 단계에서 8주문의 음이름·MIDI·간격·철자·허용 음역·정답 도달 가능성, 전체 15음 표기 map, 8마디 합주의 gate와 release 경계를 별도 스크립트로 대조했다. 문서의 상태·판정·저장·접근성 계약도 독립적으로 검토하고 발견된 불일치를 수정했다.

이 검증은 설계 문서와 콘텐츠 데이터에 대한 것이다. 아직 게임을 구현하지 않았으므로 브라우저 실행, 실제 음질·지연, 화면낭독기, 기기 내 저장, 사용자 학습효과 검증을 수행한 것으로 해석하지 않는다. 17~20장의 실제 구현 검수는 개발 단계에서 별도로 완료해야 한다.
